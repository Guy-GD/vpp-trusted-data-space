# 开发功能 Issue 与 PR 模板设计

> **文档职责**：记录本项目 GitHub 开发功能 Issue 模板和 Pull Request 模板的结构、适用范围与必填协作信息，作为后续修改 `.github` 模板文件的依据。

## 背景

项目当前处于 P0 Mock 链路开发阶段，团队按九个模块并行实现服务和前端。现有 Issue 与 PR 模板只记录目标、接口和测试，无法有效跟踪模块边界、接口契约、联调状态、数据安全和跨模块依赖。

## 目标

用一个开发功能 Issue 模板和一个 PR 模板承接所有功能开发任务，使新人能够提交可实施、可验收、可联调的任务与代码变更。

## 非目标

- 不新增 Bug、文档、部署或通用讨论等独立 Issue 模板。
- 不在模板中强制尚未确定的语言、框架、数据库或测试命令。
- 不修改分支规则、CI 工作流或 GitHub 仓库权限。

## 方案

保留现有文件位置：

- `.github/ISSUE_TEMPLATE/task.md`
- `.github/pull_request_template.md`

### Issue 模板

标题格式为 `[P0][模块名] 任务名称`。模板包含：

1. 基本信息：优先级、模块、负责人、截止时间、依赖或阻塞 Issue。
2. 目标与边界：要完成的能力，以及明确不在本任务范围内的内容。
3. 接口契约：HTTP 方法、路径、调用方、请求字段、响应字段、错误码和对应设计文档。
4. 实现要求：统一响应、健康检查、追踪、幂等和数据边界的适用项。
5. 验收标准：正常路径、失败路径、测试、网关联调、交付文件。

### PR 模板

模板包含：

1. 改动摘要和关联 Issue。
2. 模块与接口影响：新增、修改或无接口变更三选一；有变更时列出调用方、输入、输出和错误码。
3. 契约文档同步：`openapi.md`、`module-contracts.md`、`main-flow.md` 和 `response-and-errors.md` 的适用状态。
4. 验证证据：实际命令和结果、正常/失败请求、健康检查。
5. 联调与部署：网关调用状态、Mock 链路状态和 Docker Compose 影响。
6. 安全与风险：敏感数据检查、已知限制、下游依赖和回滚方式。

## 适用规则

- Issue 与 PR 仅服务于功能开发；非功能类工作暂时仍可使用普通 Issue 描述。
- 接口路径、方法、字段、枚举、状态或错误码发生变化时，PR 必须说明对应文档已同步；没有变化时必须明确标记“无接口变更”。
- 所有后端服务 PR 必须说明 `GET /health` 和统一响应是否已验证；前端 PR 必须说明仅经由 `api-gateway` 调用后端能力。
- P0 任务以稳定 Mock 与主流程联调为验收重点，不要求提前实现未排期的真实算法。
